# Plan 生成超时与可恢复轮询修复设计

日期：2026-07-30
范围：M13.2/R2 第二阶段测试环境视频主流程，以及共用 Plan 生成/修订链路

## 一、问题与实证

人工验收截图中的视频需求在选择创意方向后，两次都恰好等待 10 分钟并显示：

```text
Plan generation polling timed out
```

本地使用测试环境配置、同一条 2487 字需求、同一份表单和同一个创意方向复现后，首轮
Plan 模型 HTTPS 请求超过 10 分钟仍未收到响应，也尚未进入 Seedance 专用写作阶段。

根因由两个边界问题叠加产生：

1. `plan_llm.py` 通过 `ChatOpenAI` 调用模型时没有声明有限请求超时。
   `ChatOpenAI` 会把 `request_timeout=None` 显式传给 OpenAI Client，覆盖 SDK 自带的
   600 秒默认值，最终形成无限读等待；默认传输层还会重试两次。
2. 前端 `pollPlanJob()` 把 10 分钟当成任务失败边界。超时后
   `resumePendingPlanJob()` 清空 `pendingPlanJob`，所以仍在后端运行的任务失去恢复句柄；
   用户再次点击方向会创建第二个昂贵任务。

这相当于 Java 系统中下游 Client 没有 read timeout，而 Controller 的查询页面却先删除
了业务单号：Service 仍在执行，但用户只能重复下单。

## 二、目标

- 单次 Plan 模型请求和整个 Plan 编排都必须有明确、可测试的有限上限。
- 前端观察超时、临时网络错误、切换页面或刷新不得删除仍有效的 Plan job。
- 同一 `job_id` 只物化一条 Plan Artifact，不因恢复查询产生重复任务或重复消息。
- 初始 Plan、Plan 修订和 Seedance 专用写作共用同一超时策略。
- 超时后返回安全、满足创作合同的可审核 Plan；不得一直显示生成中。
- 保持当前 R1 Turn/Snapshot/SSE 与 `frontend_v2` 视频业务接力，不改变
  `primary_execution_intents=[]` 的安全门禁。

## 三、非目标

- 本修复不启用真实视频 Supervisor Graph Handler。
- 本修复不把现有内存异步 job 全面迁移到数据库 Operation。
- 本修复不改变 content-app Authorization 的持久化规则，也不记录 token。
- 本修复不改变视频 Provider、计费幂等键或生产发布开关。

## 四、后端设计

### 4.1 模型 Client 边界

在 Plan 专用默认模型工厂中显式设置：

- 单次请求超时：600 秒；
- 传输层自动重试：0 次。

600 秒恢复 OpenAI SDK 原本的有限默认语义；禁用隐藏重试可以确保一次 Plan 阶段最多
占用一个 600 秒窗口。业务层已有结构校验重试仍保留，因为它携带明确校验反馈，不属于
不透明网络重试。

若模型请求因超时失败：

- 初始 Plan：进入现有确定性 Plan 兜底，返回完整创作合同、时间线、分镜和资产清单；
- Seedance 专用写作：不再对同一个超时调用做第二次 600 秒重试，直接使用现有确定性
  秒段重建和稳定资产绑定；
- Plan 修订：保留当前已审核版本，返回明确失败，不污染版本历史。

### 4.2 Plan 编排总预算

Plan 生成和修订 job 增加 1200 秒总预算，防止多个合法业务校验阶段串行累积成无界等待。

- 初始生成超过总预算：使用同一请求构造确定性 Plan，并把安全超时摘要写入结果；
- 修订超过总预算：标记 job 失败，保留当前版本；
- 被总预算取消的底层线程仍受 600 秒 HTTP 超时约束，最终会释放，不会永久占用线程。

总预算属于网关 Application Service 边界，不修改共享 R1 上下文预算。

### 4.3 job 状态

Plan job 的内存快照增加向后兼容的可选字段：

- `stage`：当前阶段，如 `planning`、`seedance_authoring`、`fallback`；
- `started_at`：启动时间；
- `updated_at`：阶段更新时间。

查询接口继续使用原 `running/completed/failed` 三态，旧前端不受影响。新前端可用
`message`/`stage` 展示仍在处理，而不是用固定客户端截止时间推断失败。

## 五、前端设计

### 5.1 查询边界

删除 Plan 查询的 10 分钟终止性截止时间。只要当前对话仍可见且后端返回 `running`，
前端就继续查询同一个 `job_id`；后端 1200 秒总预算负责最终收敛。

以下情况保留 `pendingPlanJob`：

- 临时网络错误；
- HTTP 408；
- 浏览器中止请求；
- 用户切换到其他对话或页面；
- 页面刷新。

以下情况才清理：

- `completed` 且有结果；
- 明确 `failed`；
- `completed` 但缺少结果的协议错误；
- 404，表示当前网关进程已不存在该内存 job，此时提示用户从最新方向手动重试。

### 5.2 自动恢复和去重

临时查询失败时：

1. 不释放 `processedKey`，防止同一方向按钮重新启动任务；
2. 不清空 conversation context 中的 `pendingPlanJob`；
3. 当前对话仍可见时使用有限退避再次查询同一 job；
4. 切回历史对话或刷新后复用现有恢复入口；
5. 只展示一次“查询暂时中断，正在继续恢复”的状态，不重复追加错误消息。

Plan 成功物化前继续使用 `planJobId` 检查是否已有权威 Artifact，确保恢复竞态下也只保存
一次。

## 六、测试设计

先写失败测试，再改实现：

### 6.1 后端

- 默认模型工厂必须显式传入 600 秒超时和零自动重试。
- 模拟永不返回/抛出超时的初始模型，job 必须在预算内完成确定性 Plan，不得永久
  `running`。
- 模拟 Seedance 写作超时，只调用一次并走确定性绑定。
- 模拟 Plan 修订超时，当前版本和历史必须保持不变。
- job 查询返回阶段和时间字段，且仍校验用户归属。

### 6.2 前端

- 408、网络错误、隐藏和刷新都保留同一 `pendingPlanJob`。
- 明确失败、无结果完成和 404 才清理。
- 多次恢复只能查询原 `job_id`，不能再次调用 `/plan/start`。
- 成功恢复后只生成一条 Plan 消息并清理 pending。

### 6.3 真实验收

使用本机 `config.dev.yml`、测试模式前端和用户提供的临时 Authorization：

- 用原长需求验证 Plan 不再在 10 分钟时报错或丢失 job；
- 从新建对话开始完成 R1 Turn 注册、v2 视频接力、表单、方向、Plan、Plan 修改/回退、
  场景包、资产编辑/删除/重试、分镜编辑、视频生成、失败重试、合并、QC、下载、
  剪映草稿能力等全部可见按钮；
- 刷新、切换对话、折叠/展开任务看板并验证权威 Snapshot 恢复；
- 最终生成合并视频并通过下载入口完成“导出交付”。

涉及真实计费或不可逆外部动作的按钮，仍按用户已经明确授权的测试环境范围执行；测试
过程不在日志、文档或仓库中保存 Authorization。
