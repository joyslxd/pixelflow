## 结构与安全结论

- `ContextCompactionCoordinator` 相当于工作流编排 Service：只读取冻结预算和可压缩段标识，按初始统一等级累进执行外置、增量摘要、workflow 层级摘要和硬闸门动作，每步必须重新计量并保证 token 单调不增。
- 59/60、71/72、84/85、91/92 边界全部使用 M03 `TokenMeter` 的唯一阈值实现；Coordinator 会重新计算并拒绝伪造的 `compaction_level`。
- 严格低于 45% 的最大整数目标按 `(usable_input * 45 - 1) // 100` 计算；`usable_input=100` 时 44 为成功，45 不会误报成功。
- 摘要分块上限不由调用方提供。Coordinator 冻结摘要模型名和档案映射，通过 M03 `resolve_model_context_profile()`、`TokenMeter.measure()` 和 `get_context_budget_policy("summary")` 计算；缺失或过期档案自动回落到至多 128K 的保守档案。
- 消息段和 workflow 摘要段按来源顺序贪心分块，每块不超过摘要节点实际 `usable_input`；单段本身超窗时不调用摘要 Stage。85% 起先处理增量消息，再把 workflow 摘要汇总到会话层级摘要。
- 92% 下执行异常、非法 Stage 结果、token 增长、目标未达成或分块规划失败都会转入最小安全上下文；最小上下文无法证明低于可用上限时返回 `paused` 且 `model_invocation_allowed=false`，不会放行原上下文。
- 请求 DTO 拒绝额外 `business_context` 和调用方裸分块上限，只包含预算、会话 ID 与可压缩段引用；Plan、创作合同、场景蓝图、资产清单、pending action 和 operation 均不进入可变压缩状态。本切片不写库、不删除或修改原始 SQL 消息及权威业务对象。
- 未修改数据库、migration、配置、长期 feature 分支、`status/BOARD.md` 或 content-app API 文档；未提前实现 M04.4 的 conversation 锁/输入队列和 M04.5 的 Outbox 事件/`SummaryVerifier`。
