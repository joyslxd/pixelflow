## 修复目标

真实视频长对话曾把完整 Plan 修订恢复请求重复计入模型输入，使当时约
`307,110 tokens` 的业务上下文越过旧档案可用上限，并在压缩失败后被
Snapshot/SSE/Run 读取反复立即唤醒。本次修复同时冻结以下跨 R1–R4 合同：

- DeepSeek V4 Pro 物理上下文窗口为 `1,000,000 tokens`；
- 全部当前和未来 Agent/节点统一使用 `896K` 有效窗口、`32K` 输出预留、
  `32K` 安全预留，`K=1024 tokens`；
- 可用输入固定由公式计算为 `851,968 tokens`，而不是手写第二份常量；
- 实际 Runtime 必须使用当前有效且已验证的模型档案，不能走 128K 业务兜底；
- 压缩失败持久化 30 秒重试边界，边界前读取接口只读不调度；
- 恢复专用 Plan 修订数据保留在 Conversation Store，但不重复进入 Prompt。

## 实现结果

1. `ContextBudgetConfig` 成为配置 DTO，dev/prod 均逐项声明
   `effective_context_k=896`、`output_reserve_k=32`、
   `safety_reserve_k=32`、`require_verified_model_profile=true` 和
   `compaction_retry_backoff_seconds=30`。
2. `ContextBudgetPolicyProvider` 对任意非空节点名返回同一份启动快照，
   删除 Supervisor、图片、视频、PPT、视频分析和摘要节点之间的窗口分叉。
3. `deepseek-v4-pro` 的 `models[].context_profile` 在 dev/prod 都声明
   `max_context_tokens=1000000`、`max_output_tokens=32768` 和验证元数据。
4. Gateway 只把 `context_profile` 提供给 PixelFlow Runtime；
   模型 Factory 明确不把该内部字段透传给 LangChain/DeepSeek Provider。
5. Memory/SQL 压缩锁都保存 `retry_not_before`，成功路径拒绝携带重试时间，
   失败路径拒绝缺失或非未来时间。
6. Snapshot、SSE 和 Run 查询只在重试边界到达后单飞恢复，避免轮询产生重试风暴。
7. `pendingPlanRevisionRequest` 及 snake_case 别名与原有恢复专用字段一起从
   模型投影排除，权威 Store 内容保持不变。
8. `AGENTS.md`、最新设计和 `docs/agentization` 原始架构、合同、阶段计划、
   工作拆分、测试矩阵、决策、执行手册均已同步；R2、R3、R4 启动话术显式继承
   本合同。
