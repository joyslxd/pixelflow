## revision 与 CAS 合同结论

- `revision` 相当于 Java 聚合根上的 `@Version` 字段：新对话从 `1` 开始，普通更新、Runtime patch 和剪映 patch 只有在实际状态变化时才递增；no-op 不递增。
- Memory Store 在对话锁内完成比较和更新；SQL Store 在事务内使用行锁，SQLite 使用 `BEGIN IMMEDIATE`，两个 Store 并发携带同一 revision 时恰好一个成功。
- `expected_revision` 不匹配统一抛出不携带业务内容的冲突；HTTP 映射为 409。所有者条件先于 revision 比较，跨用户访问继续返回不存在，不泄露当前 revision。
- `__agent_runtime` 是服务端保留命名空间，只能由内部 Repository 方法修改。前端创建或整包 context 更新不能创建、覆盖或删除该命名空间，同时继续保留剪映双字段与恢复错误。
- Memory Store 对保存输入和返回快照均做深拷贝，普通 context、Runtime patch 与剪映嵌套对象不能通过调用方后续修改绕过 CAS。
- Alembic 迁移仅在旧对话表存在且缺少 revision 时增加默认值为 `1` 的非空列；所有权索引用于确保 downgrade 只删除本迁移创建的列。无法检查旧表的离线模式明确拒绝执行。
- PixelFlow 独立 MySQL 初始化在信息架构确认缺列时才执行兼容 `ALTER TABLE`，既有列不重复修改。
- 旧 API 路径和未携带 `expected_revision` 的旧前端请求保持兼容。
