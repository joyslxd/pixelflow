## 结构与边界结论

- Workflow 表覆盖冻结投影字段，并使用 `user_id + conversation_id` 索引支持后续所有者隔离。
- Turn 表以 `conversation_id + client_input_id` 唯一约束实现幂等结构基础，以自增 `inbox_sequence` 固定数据库接收顺序。
- ContextSummary 表保存版本、内容 hash、关键事实、证据引用和覆盖范围，不删除或覆盖原始消息。
- Event 表约束 conversation 内 `sequence` 和 `cursor` 唯一，并预留投递状态、次数和 lease 字段。
- Operation 表同时约束 `idempotency_key` 与 `workflow_id + stage + stage_version + attempt`，保存 `request_hash`、供应商任务引用和轮询 lease。
- migration 不新增外键，避免旧 PixelFlow 业务表与独立 MySQL/共享 DeerFlow 数据库初始化顺序互相阻塞；本切片通过 Repository 的 `user_id` 条件实现所有者校验的结构基础。
- 本切片不实现 SQL/Memory Repository、CAS、Turn Inbox claim 或 Event Outbox 投递，不改变旧 Store 和旧 API 行为。
