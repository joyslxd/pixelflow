# M04.4 测试报告

## 结论

M04.4 建立了 conversation 级压缩协调状态机、短事务租约、随机 fencing token 和可恢复 Turn 队列。SQL 的普通与压缩专用 Turn 入口都锁定永久协调行；`active`/`retry_required` 期间新输入只能进入 `queued`，任何领取入口都不能迁移为 `processing`。成功收尾原子切回 `idle` 并只领取最早输入；失败或暂停保留恢复标记，后续 worker 不依赖前端重发即可接管。

本切片没有实现 M04.5 的 Outbox 事件或 `SummaryVerifier`，没有修改两个长期 feature 分支、`status/BOARD.md`、运行配置或 content-app 合同。

## TDD 过程

1. 首轮新增租约与队列测试时，因 `ConversationCompactionRuntime` 尚不存在而收集失败；完成最小 Memory/SQL 实现后为 `18 passed`。
2. additive migration 首轮因新增列可空性未进入冻结预期得到 `2 failed, 82 passed`；补齐冻结结构后为 `84 passed`。
3. 自审加入“通用 claim 不得绕过恢复标记”等失败用例，先得到 `6 failed, 14 passed`；下沉阻塞语义并保留失败恢复标记后为 `20 passed`。
4. 独立审核复现两个并发缺口：普通 `SQLAgentRuntimeRepository` 可绕过专用锁、首次会话没有稳定可锁行。对应回归测试先得到 `2 failed, 20 deselected`。
5. SQL 改为每 conversation 永久协调行和 `idle | active | retry_required` 状态机；普通 `create_turn`、`enqueue_turn`、`claim_next_turn` 与压缩专用入口统一锁序。新增跨 Engine acquire/enqueue、acquire/普通 claim 竞态、空 claim 不得抢占 owner、约束状态机等测试后全部转绿。
6. 调试期间完整用例曾暴露 Memory 入队重入同一 `asyncio.Lock` 的阻塞，以及 SQL 跨 owner 空查询从“返回空”变成冲突；分别改为锁内直接幂等写入、只读 owner 隔离后回归转绿。
7. 第二轮复审发现 additive migration 下可能存在旧 Turn、但尚无协调行，错误 owner 能先占用 root。补充用例先稳定得到 `1 failed, 25 deselected`；首次创建协调行时锁定并核对既有 Turn owner 后转绿，正确 owner 仍能领取旧 Turn。
