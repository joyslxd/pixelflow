## D-002：同模块多 Codex 的隔离单位

- 日期：2026-07-22
- 状态：已被 D-004 取代
- 决策：同一模块默认顺序执行；只有运行手册标记为 `parallel_safe` 的切片可并行，每个切片必须使用独立分支、worktree、切片状态文件和文件锁。
- 原因：多个 Codex 同时写同一分支/工作区会互相覆盖 index、状态和实现。
- 影响：模块协调 Codex负责逐个把切片分支合回模块分支；合同、migration、共享状态机和视频权威链路默认不并行写入。

## D-003：M00 合同冻结后拆分 A/B 并行线

- 决策：M00 保持 5 个切片和 13.5 人时不变。M00.1–M00.2 在 `m00-contracts` 串行并产生 `contract_freeze_sha`；M00.3（B）与 M00.4（A）从该 SHA 分别在 `m00-b-web`、`m00-a-platform` 并行；M00.5 由单一集成人在 `m00-integration` 按固定顺序合并。

## D-004：模块间并行、模块内切片串行与单槽集成边界

- 日期：2026-07-22
- 状态：已确认
- 决策：M00 只保留 `m00-a`、`m00-b` 两条开发分支，两条线从同一个已评审合同/Agent 基线并行，各自内部严格串行；首次 M00 集成由开发者手动启动一次临时候选。M01–M12 每个模块只有一个模块分支和 worktree，模块内所有 1–3 小时切片严格串行，每个切片必须由开发者单独启动，Codex 不得自动连续执行整个模块。不同模块在依赖和文件所有权允许时可由多个 Codex 任务并行开发。
- 原因：切片子分支、切片 worktree、文件锁和二次合并显著增加认知与集成成本；逐切片手动启动能限制 Codex 单次任务长度，并由仓库状态、commit 和测试证据保证跨对话恢复。
- 影响：删除 `parallel_safe`、`Start-AgentSlice.ps1`、切片子分支和模块级托管话术。单个切片内的分支恢复、TDD、测试、审核、状态记录、commit、push 仍由 Codex 自动完成。普通模块最后一个切片把状态写为 `ready_for_integration` 后进入单槽集成；当前按 D-008 由开发者人工触发，失败写 `integration_blocked`。未来远端 CI 和每天 02:00 漂移检查实际启用后，才改为自动触发；已经结束的 Codex 对话不能自行唤醒。

## D-005：四阶段上线与模块中间检查点

- 日期：2026-07-22
- 状态：已确认
- 决策：采用 R1–R4 分阶段上线。R1 累计第 4 个工作日交付自动上下文压缩可感知版；R2 累计第 9 个工作日交付视频会话 Agent MVP；R3 累计第 13 个工作日接入图片/编辑、PPT 和视频分析；R4 累计第 16–18 个工作日完成全流程稳定化和新对话全面接管。
- 原因：业务需要尽早看见压缩提示和会话 Agent 的真实成果，不能等待全部 14 个模块一次性交付。

## D-006：当前无外部用户时各阶段100%发布

- 日期：2026-07-22
- 状态：已确认
- 决策：当前测试环境和生产环境尚无真实外部用户，不实现随机10%/30%/50%灰度或用户白名单。R1 获批后为 `assist + enabled_intents=[] + 100%新对话`；R2 为 `primary + enabled_intents=[video] + 100%新对话`；R3/R4 为 `primary + enabled_intents=[video,image,ppt,video_analysis] + 100%新对话`。M13.5 属于R4真实冒烟/交付切片，不新增R5。

- 影响：R1的9.17话术从 `assist+10%` 改为 `assist+100%`；R2/R3仍需分别人工批准扩大Agent接管范围，R4不再扩大比例。以后真正存在外部用户时，如需分群发布，必须另行设计基于后端认证user_id/租户的策略，不能把未实现的白名单描述为现有配置。

## D-007：中文工程交付与配置逐项说明为硬性门禁

- 日期：2026-07-22
- 状态：已确认
- 决策：本要求确认后的所有 commit/PR/合并/状态/测试/交接/发布说明使用中文主体语义；新增或修改的人工代码注释使用中文；每个新增或修改的叶子配置项必须提供紧邻的详细中文注释，不支持注释的格式使用逐键 schema `description` 或同目录中文说明。代码标识符和外部协议字段不做中文化改名。
- 原因：团队需要在不依赖原 Codex 对话的情况下直接理解提交目的、代码意图和配置影响，尤其避免配置只出现键名而无法判断默认值、生效对象、重启要求和回滚风险。
- 方案比较：仅写设计文档容易遗漏；只做自动扫描无法准确判断解释质量；最终采用“设计规范 + Codex 执行协议 + M00本地脚本门禁 + 独立reviewer”三层约束；未来远端 CI 复用同一脚本，不建立第二套规则。
- 影响：M00-A.3/M00-I.1 增加中文规范检查脚本与临时仓库测试；所有切片在 commit/push 前执行，失败不得 push、不得写集成就绪或完成状态。历史提交和未修改的旧注释不要求批量重写，规则从本决策起约束新增和修改内容。

## D-008：无远端 CI 时以本地门禁完成 M00

- 日期：2026-07-24
- 状态：已确认
- 决策：当前团队只有 Gitee Git 仓库，没有 Jenkins、Gitee 流水线或其他可用 CI 运行环境。`M00-I.1` 只要 M00 范围内的跨端合同、flag-off、Pester、Web 聚合、lint、生产构建、中文工程规范和分支自动化本地门禁全部绿色，即可把 M00 集成到 Agent，并把自动化状态写为 `automation_local_ready`。缺少远端 CI 不再是 M00 的硬阻塞，也不为不存在的 Jenkins 新增无效 `Jenkinsfile`。
- 原因：Git 仓库只负责保存代码，不能自行执行 PowerShell 门禁、单槽集成或北京时间 02:00 调度。把外部 CI 基础设施作为 M00 代码集成前置，会让已经具备本地安全脚本的 M00 被仓库外条件无限阻塞。
- 方案比较：继续要求 `automation_active` 会阻塞 M00；在没有实际远端能力时把状态伪装为 `automation_active` 会产生错误安全承诺；最终采用“本地门禁完成 M00 + 人工触发后续集成 + 未来可选远端启用”的方案。
- 测试边界：`M00-I.1` 中的“全量”只表示 M00 范围全量，不运行 M01–M13 模块门禁。M02 的 checkpointer/runtime cleanup 等定向集合在 M02 执行，后端仓库全量只在 M13 执行，二者都不能反向成为 M00 前置。
- 后续触发：状态为 `automation_local_ready` 时，普通模块到达 `ready_for_phase_integration` 或 `ready_for_integration` 后，由开发者使用执行手册第 9 节话术手动启动单槽集成；每天 02:00 漂移检查改为每次模块开工和集成前手动执行。脚本仍必须 fail-closed，失败不得更新 Agent。
- 未来启用：以后实际部署并验收远端 CI、保护分支、Webhook、单槽、失败路径和定时调度时，再单独执行运维启用任务并把状态提升为 `automation_active`；该任务不反向改变已经完成的 M00 代码验收。
